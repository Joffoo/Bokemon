# Oogiri-Flow

目标不是把每句答案压成同一种短句，而是找到**题目与笑点之间最短、最意外、最自然的连接**。核心原则是：先保护笑点，再修理表达；先判断方向是否适配，再决定是否启用该方向。

## 运行边界

本技能必须区分执行者角色：

- **主 Agent**：唯一负责读题、判断方向、调度候选生成、汇总、裁决、润色和最终交付。
- **生成 Agent**：只负责自己被分配的方向，只返回候选及极简机制标签，不修改文件，不裁决其他候选，不创建子 Agent。
- **裁判 Agent**：由主 Agent 直接调用的新上下文，只负责检查和排序候选，不再生成子 Agent，不修改技能文件。

禁止形成“主 Agent → 工作流 Agent → 三轨 Agent”的嵌套结构。若当前执行者本身是子 Agent，禁止继续调用子 Agent；由上层主 Agent 负责扁平调度。若当前环境没有子 Agent 能力，使用单 Agent 降级流程，并明确这不是独立多轨结果。

## Stage 0 主 Agent 读题与路由

1. **提取不可替代核心**（记入 `{{raw_telemetry}}`，控制在 150 字以内）：
   - 题型是文字命题、看图命题、台词命题、设定命题还是问答命题；
   - 题目要求的对象、关系、身份、动作和题眼是什么；
   - 读者必须先看见的常识场景是什么（人人秒懂的纯物理/生活底料）；
   - 哪些事实一旦改掉，答案就不再回答原题。

2. **判断三轨适配度**：分别为 A/B/C 三轨给出：`适用`、`边缘可试` 或 `不适用`，并给每轨写一句依据。不要为了形式完整强行启用三轨：
   - **A 体面破绽**：题目存在庄重身份、体面规范、权力礼仪或一本正经的公开场合，并且人物的私心、失误或小算盘能撞上它时启用。
   - **B 异业动作**：题目中的器物、动作或场景可以自然被误认成另一种明确的业务流程，并且该业务的动作能直接改变题眼时启用。没有自然的异业前提就跳过，不从行业清单硬找。
   - **C 物理死磕**：题目包含清晰可见的器物、身体动作、空间关系或可推演的物理参数，并且极端后果会反咬题眼时启用。纯人物关系、语言反转或抽象设定没有可用物理抓手时跳过。

3. **写死平庸死穴**（3 条记入 `{{forbidden_baseline}}`）：
   - [死穴 1] 现实中真会发生的社会观察叹气，或多义字字面拆字游戏；
   - [死穴 2] 套用现成网络流行语、谐音梗或万能吐槽模板；
   - [死穴 3] 抽象情绪直给或在句中替读者吐槽（角色自己绝不觉得好笑）。

## Stage 1 独立候选生成

主 Agent 直接并行调用所有被启用的生成 Agent。每个生成 Agent 只收到：题目、Stage 0 的常识核心、自己的方向说明和负面边界；不要把其他轨道的候选传给它。

生成阶段**暂不强制**：
- 14 字以内
- 句末 2～4 字落包袱
- 禁止虚词
- 固定句法
- 必须只使用一个器物

每个方向生成 3～5 条候选，优先保证笑点成立、题目贴合和画面/语境清楚。每条候选附一个不超过 6 字的内部机制标签，例如“身份误认”“礼仪露馅”“物理反咬”；不要写长篇解释。最终候选正文可以是完整自然句，标点和长度暂不作为淘汰条件。

拼装规范（与 `index.html` 的 `buildDivergenceSystemPrompt` 逐字一致）：

```

各方向互不参照、互不借用对方的词。请依次完成已启用方向的候选生成。全部完成后再输出，顺序如下。

（下文 Subagent A 提示词块原文）

【输出契约】只输出合法 JSON，除 JSON 外无任何字符：
```

## Stage 2 独立裁判（候选已匿名隐藏来源和轨道）

### 第一步：硬伤证伪（逐条检查并给出单一死因）
逐条审查匿名候选，任一不过即淘汰并给出单一死因：
1. 是否真正回答原题，而不是只借用了题目中的一个词。
2. 读者是否能在一次阅读内补齐关键场景；若必须听作者解释，淘汰。
3. 是否只是现实观察、普通吐槽、谐音或现成网梗。
4. 是否有两个以上互不咬合的概念硬拼。
5. 是否依赖错误事实或不属于题目的外来背景。
6. 是否只有“奇怪”而没有具体意外、目的反咬或人物暴露。
7. 句子本身是否自然通顺。
若全灭，照实报告全灭，严禁为了保留名额而复活答案。

### 第二步：相对排序与胜出判定
幸存者按四项分别给 1～5 分，不合并成含糊的总印象：
- 题目贴合（1-5）
- 一秒可见性（1-5）
- 意外与落差（1-5）
- 语言自然度（1-5）
另标记：`需要解释`、`像模板`、`笑点机制重复`。
裁判必须说明最强候选胜出的具体原因，不写“很有趣”“很高级”这类空泛赞美。决出最佳原句（initial_champion）。

## Stage 3 主 Agent 终审与可选润色（先保护笑点，再修理表达）

主 Agent 读取裁判报告，先保留最佳原句，不自动重铸。
- 只有以下情况才润色：原句已有成立的笑点，但存在明显赘字、包袱提前泄露、动作不清或语法卡顿。
- 润色时最多尝试两版，并锁定原句的核心器物、人物关系和错位机制。
- 改写后必须与原句并排比较：如果只是更符合格式，却没有同时提高自然度或清晰度，保留原句！
- 14 字以内、句末落点、少虚词只能作为短句任务的优先优化项，不能单独成为淘汰理由。题目明确要求短句时，再进行压缩；压缩损害理解时，以理解为准。
- 确定全场总冠军（final_champion）。

## Stage 4 交付

【**极简交付原则**】
严禁向用户展示路由、候选、裁判记录或内部推理。一切推理、筛选与裁决均在后台完成，**最终回复只输出最终结果**。

### 图像命题
把最终全场总冠军压到原图上：
```bash
python scripts/render_meme.py "<图片路径>" "<金句>" "00-Inbox/<输出文件名>.png"
```
交付只回复：
1. 压制生成的图片（Obsidian 嵌入引用 `![[<输出文件名>.png]]`）；
2. 最终金句文本。

### 文字命题
直接回复最终全场总冠军金句。
如确有同等质量的变体，最多附 1～2 句。

## 降级流程

没有子 Agent 能力时：主 Agent 先完成三轨适配判断，再在同一上下文中按启用顺序生成候选，随后清空当前生成思路并执行独立复核清单。交付时标记为“单 Agent 降级模式”，不得宣称完成了独立多轨和独立裁判。

若 Oogiri-Flow 被其他工作流调用：外层工作流必须把三轨生成和裁判作为扁平任务直接调度；本技能不得尝试继续创建子 Agent。若外层没有这种调度能力，采用降级流程。
